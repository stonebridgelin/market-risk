## 三、拦截插件及其自测

`tests/v20_data_guard.py` 只在 `-p tests.v20_data_guard` 显式加载时生效，不修改 `conftest.py`、`pyproject.toml` 与任何既有测试。

- 拦截时抛出专用异常类 `V20DataGuardBlocked`（`PermissionError` 的子类）。归类只认这个类（沿异常链查找），不以报错文字判断。
- “未完成（被拦截）”分两种来源分别计数：直接拦截（有拦截记录）；夹具缓存（没有拦截记录，测试失败或出错且异常链里有专用异常类）。
  清单写明夹具名，以及它最初被拦截的测试名。
- 跳过、预期失败、意外通过按 pytest 的原结果单列；有拦截记录的仍报告“未完成（被拦截）”，有子进程或 ctypes 记录的仍列入覆盖不完整的清单。
- 记录模式不抛异常、不注册夹具、不修改收集结果与测试结果、不修改退出码，终端摘要只追加记录段落。

自测 `tests/test_v20_data_guard.py` 分两层：

- **（一）纯逻辑**：模式解析、路径判定、事件决定、口径汇总、异常链查找、记录文件格式，都用构造输入在进程内测试。
  自测代码自身不调用 `sys.addaudithook`，也不在本进程加载插件。
  这不表示运行环境没有钩子：日常检查中，这些自测运行在已由外层 `-p tests.v20_data_guard` 安装了拦截钩子的 pytest 进程内。
- **（二）钩子的实际行为**：4 个测试，各自用 `subprocess.run([sys.executable, "-m", "pytest", ...])` 启动相互独立的子进程：
  不加载插件与记录模式的对照（逐项结果、退出码、读到的内容逐字节相同）；拦截模式；非法取值；
  共享夹具被拦截后后续测试归“夹具缓存”，以及抛出普通 `PermissionError` 的测试仍归“失败”的反例。

**外层拦截器对第二层的归类：通过但覆盖不完整。** 这些自测本身启动子进程，子进程中的访问不在外层拦截范围内。
隔离措施是：子进程只在本次自测的临时目录运行；受保护目录由 `V20_GUARD_ROOT` 指向临时目录中的构造目录；
用临时目录里的最小 `pytest.ini` 与 `--rootdir`、`--basetemp`、`-p no:cacheprovider`，不加载仓库的 `conftest.py` 与 `pyproject.toml` 设置；
构造测试的源码在写出前经静态检查，不含受保护数据目录的写法。
以上是隔离措施，不是已证明子进程未读取 `data/market/` 的证据。
