## 一、改动清单

新增纯计算模块：

- `wavewarn/condition_trace.py`：重放一个设定的通道与状态机，逐日记下各转绿条件是否成立。灯色仍由 `state_machine.step_system` 给出；每天核对“各条件全部成立”与状态机的 Ready 一致，不一致即报错。
- `wavewarn/bottleneck.py`：各条件首次成立天数、事件类别、瓶颈判定与汇总行。
- `wavewarn/lighting_reasons.py`：执行非绿区间的主分类（A、B、C）与细分原因。
- `wavewarn/period_stats.py`：逐年统计、期间的按暴露累计收益与最大回撤。
- `wavewarn/diagnostics_v13.py`、`diagnostics_v13_report.py`：四项诊断的编排、表格行与报告正文。

新增读写边界 `wavewarn/diagnostics_v13_run.py`；入口 `services.wavewarn_diagnose_v13` 与 CLI `wavewarn diagnose-v13`。

对既有代码的改动只有重构，不改行为：

- `evaluation.py`：把“一个设定的通道谓词与 Ready 输入”抽成 `candidate_channel_setup`，把特征计算抽成 `grid_features`，供状态序列、收敛检查与诊断共用。

## 七、实现中的口径说明

1. **条件 (7) 的操作化。** 您确认的瓶颈定义以“连续成立期”为准，所以我把 (7)“系统从红转黄”按状态“系统不处于红灯”处理：
   - 判瓶颈时，取包含信号日的那段非红期的起点（即由红降黄的那一天）；只有它前一日的红灯不早于事件高点 P 时才参与，对应“事件中出现过红灯”。
   - 首次成立天数：只在 [P, 搜索上限] 内出现过红灯时填写，为 Tr 起第一个不在红灯的日子；若红灯在 Tr 之前已经结束，记 0。
   这一条是我对 (7) 的落地方式，原文没有逐字规定；如果您希望“首次成立天数”改为“Tr 之后第一次由红降黄的那一天”，只需改一个函数重跑。
2. **首次成立天数的统计范围**是全部纳入事件（含类别①、③）；(8) 的信号日与执行日只有类别②事件有值。
3. **亮灯原因的条件粒度**与登记的条件一致：“两指数 Q≥K”“两指数高于 MA50”各作为一个条件，不拆到单个指数；两项广度修复分列。
4. **熊市期间的区间**取起点在 [高点日, 低点日) 的区间，最后一个区间止于低点日收盘。
5. **报告里的中位数、P75** 用与退出代价相同的线性插值分位数。
