# 0001 数据存储架构

- 状态：已采纳（2026-09-27）
- 相关：`docs/STORAGE.md`、`docs/SPEC.md` 第6节、`data/market/README.md`、`db/sql/README.md`

## 背景

阶段6（逐日历史回测）之前需要确定三件事：评分输入从哪里读；数据库存什么、用哪种数据库；以后接入 FastAPI、Vue 前端或部署到服务器时，数据库能否平滑切换。

在此之前，评分每次按基准日直接读取接口缓存（`data/cache/`），缓存不提交 git。这带来两个问题：一是同一基准日的输入没有统一的版本，难以复现；二是逐日回测要为几千个基准日分别下载窗口数据，重复且浪费。

## 决定

### 1. 数据库继续使用 SQLite

理由：
- 单用户使用，数据量小（运行记录、分数、指标、标签、索引）；
- 程序内读写更快，零运维；
- 备份就是复制文件；
- 测试与正式运行使用同一种数据库，行为一致。

### 2. MySQL 作为已验证的备选

阶段7、8 若部署到服务器，或需要多个客户端同时访问，只需修改 `DATABASE_URL` 即可切换。为保证这一点：
- 访问统一经 SQLAlchemy Core，不使用任何数据库的专有语法；小数用 `Numeric`，日期用 `Date`；
- 提供可重复执行的验证命令 `market-risk db verify-mysql`：在 `.env` 的 `MYSQL_VERIFY_URL` 指向的专用库上执行 Alembic 迁移和 `rebuild-db`，再与 SQLite 逐表逐行比对，并用导出的 SQL 建库核对；另有默认跳过的集成测试（`pytest -m mysql`）；
- 验证完成后，日常的 `DATABASE_URL` 仍指向 SQLite。

### 3. 数据按性质分三处存放

| 类别 | 位置 | 格式 | git | 说明 |
|---|---|---|---|---|
| 原始资料 | `data/manual/`（含 `tradingview/raw/`）、`data/legacy/`、`data/materials/` | 原始文件 | 提交 | 人工录入、导出文件、截图时代记录；只读或只追加 |
| 市场数据 | `data/market/` | 每个序列一个 CSV，另有 `manifest.json` | 提交 | 由 `data build` 从接口缓存（按需下载）、TradingView 清洗结果和手工录入生成；**评分与逐日回测一律从这里读取** |
| 分析结果 | `db/market_risk.sqlite`（及 `results/` 运行目录） | SQLite | 数据库不提交；`results/` 提交 | 数据库只存分析结果与索引，可随时由文件重建（`rebuild-db`） |

- 接口缓存（`data/cache/`）只作为 `data build` 的输入，不提交。
- 市场时间序列不存入数据库。
- 数据集的历史数值被修订时，`data build` 列出修订清单、不自动覆盖，确认后才更新（`--accept-revisions`）。
- 运行目录的 `meta.json` 记录 `data/market/manifest.json` 的 sha256 作为数据集版本；`data/market/` 有未提交修改时，运行结果不能自动设为正式记录。

### 4. 表结构以 Alembic 为唯一源头

- 迁移脚本在 `migrations/versions/`；`storage/schema.py` 描述最新结构，并有测试保证两者一致。
- `db/sql/` 下的 SQL 文件（`01_schema_sqlite.sql`、`01_schema_mysql.sql`、`02_base_data.sql`）由 `market-risk db export-sql` 自动导出，不得手工修改；有测试保证表结构或 YAML 变化后已重新导出。
- 参考表（标的登记、休市日历、裁定日期表）的内容由 `config/` 下的 YAML 生成，YAML 仍为源头；供以后的前端与统计查询使用。

## 后果

- 评分输入可复现：同一数据集版本（manifest sha256）下，同一基准日的计算结果相同。
- 逐日回测只读本地 CSV，不再逐日下载。
- `data/market/` 的更新会出现在 git 历史中，每次 `data build` 的变化可审查。
- 更换数据库只需修改连接地址，并先运行 `db verify-mysql` 等验证。
