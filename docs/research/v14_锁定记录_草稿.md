## 正式锁定的操作步骤（验证期命令会逐项核对）

1. 把全部代码、配置、规格合并到要运行的分支并提交；记下这个提交号 C（`git rev-parse HEAD`）。
2. 复制本草稿为正式记录（例如 `docs/research/v14_锁定记录_YYYY-MM-DD.md`），去掉开头十行内的“草稿”字样，沿用本草稿的字段名：
   - “代码提交号”填 C；
   - “此前失败的运行”：没有失败记录时填“无”；有失败记录时逐一列出其文件名（写在反引号内），并说明修复改动；
   - 四份规格与三份配置的 SHA-256 填它们**在提交 C 中已提交内容**的哈希（LF 换行）。用 `git show C:路径` 的内容计算，不要用工作区文件（本机检出时可能把换行转成 CRLF）；
   - 补齐“确认原文”“负责人确认日期与原文”。
3. 把正式记录**单独作为一次提交**（这次提交只包含这一个文件）并推送。
4. 预检：`uv run market-risk wavewarn v14-lock-check --lock-record <正式记录路径>`。它只核对、不读取任何数据；不通过时会一次列出全部问题。
5. 正式运行（只能一次）：`uv run market-risk wavewarn v14-validate --lock-record <正式记录路径>`。

验证期命令在以下任一情形拒绝运行：HEAD 相对于 C 的差异不是恰好只有锁定记录这一个文件；工作区有未提交的改动或未跟踪的文件；任一规格或配置的 SHA-256 与记录不一致；记录是草稿；选定设定不是 K=5、θ_P=2.5%；随机种子或重抽样次数与配置不一致；记录的“此前失败的运行”字段没有列出 `reports/research/wavewarn_v14/validation_failures/` 中的全部失败记录；输出目录 `reports/research/wavewarn_v14/validation/` 已存在；找不到 git。

全部计算在内存与临时目录中完成，成功后才一次写入正式输出目录（其中的 `lock_record.json` 记有锁定记录的 SHA-256、运行时的 HEAD 与逐日明细压缩前后的哈希）。中途失败时正式输出目录不创建，只写一份不含任何数值的失败记录；此后须按“验证期运行的失败处理”一节新建修复提交、把失败记录一并提交，并写新的正式锁定记录后才能再次运行。
